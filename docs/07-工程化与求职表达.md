## 3. README 应回答什么？

- What：评估哪种推理负载、哪款模型、哪个推理引擎？
- Why：为什么 TTFT、TPOT、P95 和总吞吐量都要测？
- How：环境依赖、运行命令、输入输出、截图。
- Results：真实数字、固定环境和运行参数。
- Caveats：实验局限、未对齐的 baseline、缓存和并发因素。
- Roadmap：进一步验证和扩展方向。

## 4. 建议的简历写法（**实测范围内**）

> **LLM Inference Benchmark | Python / vLLM / PyTorch / WSL2 / CUDA**  
> 基于 Qwen2.5-0.5B-Instruct 在 RTX 3060 Laptop 上搭建 vLLM 本地推理 API，开发面向单请求及并发负载的 Python Benchmark 工具；实现客户端流式 TTFT/TPOT、吞吐量、平均/P95 延迟、重复测试统计、错误计数与 CSV/JSON 自动归档，并使用 Matplotlib 可视化；在固定短文本实验中观察到 128 并发下约 **7.7k output tokens/s** 系统总吞吐量，分析批处理收益与单请求延迟的权衡。

不要写：**“我让模型推理速度提升了 13 倍”** 作为被严格验证的事实。若要描述，应写“在未严格对齐的历史两套脚本中，观察到约 13× 的输出吞吐率差异；后续计划进行同条件验证”。

## 5. 可以回答的面试问题

| 可能被问 | 回答重点 |
|---|---|
| Transformers 与 vLLM 区别 | 模型架构没变，服务调度/内存/算子/批处理不同 |
| 为什么 vLLM 的吞吐量随并发上升？ | GPU batch 利用率上升；总吞吐与每请求速度区分 |
| TTFT 与 TPOT 分别由哪些环节构成？ | 排队/预填充/首个输出 vs 后续 Decode / 传输 |
| 什么是 KV Cache？ | 避免重复计算历史上下文 K/V，容量影响并发 |
| 为什么 P95 比均值重要？ | 揭示尾部体验，但小样本不稳定 |
| 怎么解决 WSL 无法下载模型？ | 分层排查：公网正常、目标受限、代理传递失败；Mirrored/autoProxy |
| 为什么缺 nvcc 还能使用 GPU？ | driver/runtime 用于执行编译好的算子；JIT 路径才可能需要编译器 |
| Benchmark 最大缺陷是什么？ | 历史基线不同条件；缓存、固定短 Prompt、客户端瓶颈、无服务端 profiling |

## 6. 下一项目衔接建议

与其无限加并发，不如转向更有价值的 **GPU 推理系统优化**：

1. **控制变量比较 Transformers vs vLLM**（同机同权重同 Prompt 同输出规模）；
2. **深入 vLLM 的请求调度、PagedAttention、KV Cache block 管理**；
3. 用 `nvidia-smi`、vLLM `/metrics` 与 profiler 联动，定位瓶颈；
4. 再考虑量化或多模型服务。

从“懂指标”到“能解释指标为什么变化”，是从使用工具到做系统工程的跃迁。
